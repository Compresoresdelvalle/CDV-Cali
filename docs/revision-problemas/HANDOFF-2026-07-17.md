## 1. Qué es esta campaña

Auditoría profunda **sección por sección** de la app (React 19 + Vite + Zustand +
Supabase), **en producción con datos reales de un negocio activo**. Cada sección:

1. **Cacería**: un `Workflow` lanza 6 cazadores Sonnet en paralelo
   (backend / forense-datos / frontend / contrato / negocio / ux) + verificación
   adversarial por hallazgo (veredictos: CONFIRMADO / REFUTADO / CODIGO_VIEJO /
   PLAUSIBLE). Scripts base: `wf-s7.js`, `wf-s8.js` en el scratchpad de la sesión.
2. **Informe al dueño** con los hallazgos deduplicados + `AskUserQuestion` para
   las decisiones que son suyas (política de negocio, remediación de datos).
3. **Implementación**: Fable/Opus hace el frontend; **un agente Opus en background
   ejecuta TODA escritura a la BD de producción**.
4. **Verificación adversarial final**: otro workflow de ~6 flujos que intenta
   REFUTAR que el trabajo quedó bien (ha encontrado bugs reales cada vez).
5. Registro + commit + push.

### Reglas inviolables (respetarlas siempre)

- **BD de producción es SOLO LECTURA durante la cacería.** Toda escritura la hace
  el agente Opus, y **siempre** se prueba antes dentro de `BEGIN ... ROLLBACK`.
- **Nunca DELETE/TRUNCATE físico** de datos. Soft delete con `activo`.
- **No tocar**: auth, el candado append-only de `movimientos`, ni ampliar alcance
  a ventas/cierres sin autorización.
- **Regla del código viejo**: antes de "arreglar" algo, validar si es código VIVO
  o código muerto/legacy/dato histórico. Si un "error ya resuelto" resulta ser
  código viejo, **dejarlo como estaba** (el dueño teme que se dañe lo que ya sirve).
- **Ningún fix se implementa sin aprobación explícita del dueño.** Presentar
  hallazgos primero.
- **Los bugs se corrigen al encontrarlos** (no se acumula backlog).
- Testing solo en prod; productos de prueba: referencia `TEST-PRUEBA%` (están
  `activo=false`; reactivar solo dentro del BEGIN/ROLLBACK).
- Migraciones aplicadas por MCP no crean archivo local → hay que materializarlas
  leyendo `supabase_migrations.schema_migrations`
  (`array_to_string(statements, E'\n')`) y escribiendo el `.sql` en
  `supabase/migrations/`.

Query para regenerar la lista completa (solo lectura):

```sql
WITH guard_ts AS (SELECT '2026-06-11 14:53:00'::timestamptz AS t),
recep AS (
  SELECT c.id AS compra_id, c.fecha_recepcion, dc.producto_id, dc.cantidad, dc.costo_unitario
  FROM compras c JOIN detalle_compra dc ON dc.compra_id = c.id
  WHERE c.recibida = true AND c.fecha_recepcion >= (SELECT t FROM guard_ts)
    AND coalesce(c.estado::text,'') <> 'cancelada' AND dc.cantidad > 0
),
perdidas AS (
  SELECT r.* FROM recep r
  WHERE NOT EXISTS (
    SELECT 1 FROM productos_precio_costo_log l
    WHERE l.producto_id = r.producto_id AND l.campo = 'costo_promedio'
      AND l.created_at BETWEEN r.fecha_recepcion - interval '5 minutes'
                           AND r.fecha_recepcion + interval '5 minutes'
  )
),
esperado AS (
  SELECT producto_id,
         round(sum(cantidad * costo_unitario) / nullif(sum(cantidad),0)) AS costo_esperado
  FROM perdidas GROUP BY producto_id
),
stock AS (SELECT producto_id, sum(cantidad) AS stock_global FROM inventario GROUP BY producto_id)
SELECT p.referencia, p.nombre, round(p.costo_promedio) AS costo_actual, e.costo_esperado,
       coalesce(s.stock_global,0) AS stock,
       round(abs(e.costo_esperado - p.costo_promedio) * coalesce(s.stock_global,0)) AS descuadre
FROM esperado e
JOIN productos p ON p.id = e.producto_id
LEFT JOIN stock s ON s.producto_id = e.producto_id
WHERE p.activo = true AND abs(e.costo_esperado - p.costo_promedio) > 1
ORDER BY descuadre DESC NULLS LAST;
```

## 5. Deuda P3 documentada (latente, decidido NO tocar)

### Traspasos (S7)

- `detalle_traspaso.cantidad_recibida` tiene `DEFAULT 0`, lo que hace código
  muerto el `COALESCE` del trigger de entrada. Si un flujo futuro marcara
  `recibido` sin setear `cantidad_recibida`, habría **merma total silenciosa**.
  Hoy no explotable (REST bloqueado, la RPC siempre la escribe).
- `movimientos.stock_posterior` mezcla bolsillos: un reporte que sume sin mirar
  `observaciones='Insumo'` mezclará venta e insumo.
- `usuario_id` del asiento de entrada = quien creó el traspaso, no quien recibió
  (preexistente, aplica a ambos bolsillos).
- `fn_crear_traspaso` no pre-valida stock al crear; el bloqueo real está al
  enviar con `FOR UPDATE`.

### Ensambles (S8)

- El consumo de insumos ocurre al **armar la receta**, no al completar: un
  ensamble en proceso retiene insumo. **Es el diseño** (reserva física real).
- El técnico asignado NO puede editar la receta (solo creador/Admin) — más
  estricto que el flujo dibujado; se dejó así.
- `anon` conserva SELECT en `ensambles` (RLS decide qué ve).
- El patrón del flag `app.costo_sistema` es frágil si algún día se envuelve ese
  tramo en `BEGIN/EXCEPTION` (hoy inocuo: la excepción aborta la tx y el flag es
  transaction-local).
- El producto del ensamble #23 (CABEZOTE 2080 RF 5HP SEG) tiene `referencia = ''`
  (cadena vacía) → dificulta búsqueda/QR.
- **El costo_promedio $480.000 del producto del #23 se conservó a propósito**
  (edición manual del Admin). **EXCLUIRLO de cualquier recálculo genérico futuro**
  o se pisará a $111.350.
